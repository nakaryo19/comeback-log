# エラーログの運用

本番で起きたエラーを `error_logs` テーブルに記録している（リリース計画 B5）。
このドキュメントは、その**見方**と**消し方**をまとめたもの。

関連: `supabase/migrations/20260816120000_add_error_logs.sql` /
`lib/errorReporter.ts` / `lib/supabase/errorLog.ts`

## なぜ外部の監視サービスを使っていないか

CLAUDE.md の制約は「観測するな」ではなく **「感情ログを外部へ送るな」**。
自前の Supabase は既に感情ログ本体を保持している場所なので、ここへ書くかぎり
**新しい信頼境界を一つも増やさない**。第三者提供の記載も、App Store の
プライバシーラベルへの事業者追加も要らない。

Sentry 等を見送ったのはコストの問題ではなく、この規模で釣り合わないため。
**再検討する条件**：自分では再現できない不具合の報告が届き始めたとき。
そのときは `lib/errorReporter.ts` の `setErrorSink()` を差し替えれば済むよう、
送信先を1箇所に閉じてある。

## 何が記録されないか（誤解しないこと）

この仕組みで**見えない**ものが3つある。埋められていると思い込まないこと。

| 見えないもの | 理由 | 代わりに見る場所 |
|---|---|---|
| 通信できなかったエラー | 記録先が Supabase なので、そもそも書けない | — （直せる不具合ではない） |
| ネイティブのクラッシュ | JS 側の仕組みでは拾えない | App Store Connect / Xcode Organizer |
| ログイン前のエラー | RLS が `auth.uid() = user_id` を要求する | — |

ログイン前を諦めたのは、匿名 insert を許すと**誰でも無制限に行を積める口**に
なるため。無料枠のDBを守るほうを優先した。

## 見る

Supabase ダッシュボード → SQL Editor。**select ポリシーを作っていない**ため、
アプリからは読めない（ダッシュボードは service_role で動くので読める）。

```sql
-- 直近1週間を、多い順に
select context, message, app_version, platform, count(*), max(created_at)
from error_logs
where created_at > now() - interval '7 days'
group by context, message, app_version, platform
order by count(*) desc;
```

**件数で見る。** 1件だけのものは端末固有の事情であることが多く、
同じ `message` が複数ユーザー・複数日にまたがっているものが直す価値のある不具合。

```sql
-- 特定のエラーの詳細（スタックを読む）
select created_at, app_version, stack
from error_logs
where message like '%PGRST%'
order by created_at desc
limit 20;
```

## 消す

**保存期間の管理は手動。** 無料プランでは pg_cron を前提にできない。
月に1度、次を実行する。

```sql
delete from error_logs where created_at < now() - interval '90 days';
```

90日にしているのは、「前のバージョンで直したはずのエラーが再発していないか」を
見るのに1〜2回のリリースサイクルぶんあれば足りるため。

放置すると無料枠の容量を食う。異常な量が溜まっていたら、消す前に
**何が大量に出ているのかを必ず確認する**（それ自体が不具合の兆候）。

## 記録する内容を増やすとき

`lib/errorReporter.ts` の `ErrorReport` に項目を足すことになるが、
**利用者が入力した内容は載せない。** 感情の記録の自由記述はもちろん、
タスク名や目標名も入れない。プライバシーポリシー第2条(2)で
「利用者が入力した内容を含めることはありません」と宣言している。

例外メッセージ自体に DB が値を含めてくることがある（一意制約違反など）ため、
`errorReporter.ts` で長さを打ち切っている。この打ち切りを外さないこと。
