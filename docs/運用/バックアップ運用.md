# バックアップ運用

Supabase 無料プランには**バックアップ機能が一切ない**。誤ったマイグレーションやデータ破損が起きても、
無料枠には復旧手段が存在しない。そのため自前でバックアップを確保する。

このアプリの価値は「記録を積み重ねて自分の攻略法に気づく」ことにあり、
蓄積された感情ログを失うことは、ユーザーにとってアプリを使う理由そのものを失うことに等しい。
バックアップは付加機能ではなく、無料枠で運用を続けるための**前提条件**として扱う。

## 仕組み

| 要素 | 内容 |
|---|---|
| 実行 | `.github/workflows/backup.yml`（毎日 03:37 UTC ＋ 手動実行） |
| 取得 | `scripts/backup-db.sh` が `pg_dump` を実行 |
| 対象 | `public` スキーマ全体（スキーマ定義＋データ）と `auth.users`（データのみ） |
| 暗号化 | `gpg --symmetric --cipher-algo AES256` |
| 保管 | GitHub Actions Artifacts（保持期間 90日） |

### 暗号化が必須である理由

ダンプには `emotion_logs.free_text`（感情ログの自由記述）が**平文で含まれる**。
CLAUDE.md の「感情ログは、いかなる場合も外部API送信・公開プロフィールへの露出をしてはならない」という
方針に従い、GitHub の Artifacts に置く前に必ず暗号化する。

復号パスフレーズは GitHub Secrets にのみ存在し、Artifacts 単体からは復元できない。

### 副次的な効果：自動停止対策としても働く

`pg_dump` は実際のDB活動になるため、`keep-alive.yml` の RLS 0行クエリよりも確実な
自動停止対策として機能する（`docs/運用/Supabase自動停止対策.md` 参照）。
バックアップと keep-alive は時刻をずらしてあり、片方が壊れてももう片方が活動を記録する。

## 初期設定

### 1. GitHub Secrets を登録する

| Secret 名 | 値 |
|---|---|
| `SUPABASE_DB_URL` | Supabase の **Session pooler** 接続文字列 |
| `BACKUP_PASSPHRASE` | バックアップ暗号化用のパスフレーズ（自分で生成） |

**接続文字列は Session pooler のものを使うこと。** Direct connection（`db.<ref>.supabase.co`）は
IPv6 のみの場合があり、GitHub Actions のランナー（IPv4）から到達できない。
Supabase ダッシュボードの Connect から「Session pooler」の接続文字列をコピーする。

パスフレーズの生成例：

```bash
openssl rand -base64 32
```

**このパスフレーズを失うとバックアップは永久に復号できない。**
パスワードマネージャ等、GitHub とは別の場所に必ず保管すること。

登録コマンド：

```bash
gh secret set SUPABASE_DB_URL
gh secret set BACKUP_PASSPHRASE
```

### 2. 手動実行して動作を確認する

```bash
gh workflow run backup.yml
gh run list --workflow backup.yml --limit 1
```

### 3. 復旧できることを一度検証する ★必須

**未検証のバックアップは、無いのと同じ。** 初回設定時に必ず一度は復号まで通すこと。

```bash
# Artifacts をダウンロード
gh run download <run-id> --name db-backup-<run-id>

# 復号して展開
BACKUP_PASSPHRASE='...' ./scripts/restore-db.sh comeback-log-*.tar.gz.gpg

# public.sql に自分のタスク・感情ログが含まれているか目視で確認する
```

確認後、展開した平文ファイルは削除すること。

## 日常の運用

### マイグレーション適用前

**必ず手動でバックアップを取る。** 最も現実的な事故がここで起きる。

```bash
gh workflow run backup.yml
```

完了を確認してからマイグレーションを適用する。

### 定期確認（月1回程度）

```bash
gh run list --workflow backup.yml --limit 10
```

成功が並んでいること、アーカイブのサイズが極端に小さくなっていないことを確認する。
スクリプトは 1KB 未満のアーカイブをエラーとして扱うが、目視確認も併用する。

## 復旧手順

1. 対象の Artifacts をダウンロードする
2. `scripts/restore-db.sh` で復号・展開する
3. **中身を確認する**（想定した日付範囲のデータが入っているか）
4. 接続先が復旧対象のプロジェクトであることを確認したうえで、手動で流し込む

```bash
psql "$SUPABASE_DB_URL" -f restored/public.sql
```

`public.sql` は `--clean --if-exists` 付きで作られているため、
**既存の public スキーマのテーブルを削除してから作り直す。**
実行先を間違えると本番データを消す。接続文字列を必ず確認すること。

復旧を自動化していないのは意図的である。復旧は上書き操作であり、
自動化すると誤実行時の被害が大きくなるため、人間が中身を見てから実行する設計にしている。

### プロジェクトごと失った場合

`auth.users` のダンプが必要になる。`goals.user_id` は `auth.users(id)` を参照しているため、
ユーザー行を先に復旧しないと外部キー制約で失敗する。

1. 新しい Supabase プロジェクトを作成し、`supabase/migrations/` を適用する
2. `auth_users.sql` を流し込む
3. `public.sql` を流し込む

`auth_users.sql` はベストエフォートで取得しているため、存在しない場合がある
（その場合はアーカイブ内に `auth_users.SKIPPED` が入っている）。
この経路は Supabase 側の内部スキーマ変更に影響を受けやすいので、
プロジェクト全損は「keep-alive とプラン移行で予防する」ことを主とし、
このバックアップは最後の手段と位置づける。

## 制約

- **Artifacts の保持期間は最大90日。** それより長く残したい時点のバックアップは、手動でダウンロードして保管する
- **GitHub 上に暗号化データが置かれる。** パスフレーズの強度と保管がそのまま安全性になる
- **`auth.users` の復旧はベストエフォート。** 上記の通り
- 保存先を GitHub 以外（自己管理ストレージ等）に変えたい場合は、`backup.yml` のアップロード先を差し替える
