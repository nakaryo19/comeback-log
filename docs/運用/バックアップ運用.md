# バックアップ運用

Supabase 無料プランには**バックアップ機能が一切ない**。誤ったマイグレーションやデータ破損が起きても、
無料枠には復旧手段が存在しない。そのため自前でバックアップを確保する。

このアプリの価値は「記録を積み重ねて自分の攻略法に気づく」ことにあり、
蓄積された感情ログを失うことは、ユーザーにとってアプリを使う理由そのものを失うことに等しい。
バックアップは付加機能ではなく、無料枠で運用を続けるための**前提条件**として扱う。

## 仕組み

| 要素 | 内容 |
|---|---|
| 実行 | `.github/workflows/backup.yml`（毎日 03:37 UTC ＋ 手動実行） |
| 取得 | `scripts/backup-db.sh` が `pg_dump` を実行 |
| 対象 | `public` スキーマ全体（スキーマ定義＋データ）と `auth.users`（データのみ） |
| 暗号化 | `gpg --symmetric --cipher-algo AES256` |
| 保管 | GitHub Actions Artifacts（保持期間 90日） |
| 復元検証 | `.github/workflows/verify-restore.yml`（手動実行）＋ `scripts/verify-restore.sh` |

### 暗号化が必須である理由

ダンプには `emotion_logs.free_text`（感情ログの自由記述）が**平文で含まれる**。
CLAUDE.md の「感情ログは、いかなる場合も外部API送信・公開プロフィールへの露出をしてはならない」という
方針に従い、GitHub の Artifacts に置く前に必ず暗号化する。

復号パスフレーズは GitHub Secrets にのみ存在し、Artifacts 単体からは復元できない。

### 副次的な効果：自動停止対策としても働く

`pg_dump` は実際のDB活動になるため、`keep-alive.yml` の RLS 0行クエリよりも確実な
自動停止対策として機能する（`docs/運用/Supabase自動停止対策.md` 参照）。
バックアップと keep-alive は時刻をずらしてあり、片方が壊れてももう片方が活動を記録する。

## 初期設定

### 1. GitHub Secrets を登録する

| Secret 名 | 値 | 例 |
|---|---|---|
| `SUPABASE_DB_HOST` | Session pooler のホスト名 | `aws-0-ap-northeast-1.pooler.supabase.com` |
| `SUPABASE_DB_USER` | pooler 用のユーザー名 | `postgres.<project-ref>` |
| `SUPABASE_DB_PASSWORD` | データベースパスワード | （そのまま。エンコード不要） |
| `BACKUP_PASSPHRASE` | バックアップ暗号化用のパスフレーズ | 自分で生成 |

**接続情報を1本の URL にまとめていないのは意図的である。** 理由は2つ：

1. パスワードに `%` `&` `!` などが含まれると、URL として解釈されて壊れる
2. 接続失敗時のエラーメッセージにパスワードの一部が出力されることがあり、
   **公開リポジトリの Actions ログに残る**（実際に一度発生し、パスワードのローテーションが必要になった）

個別の環境変数にして `PGPASSWORD` で渡せば、どちらも構造的に起こらない。

#### 接続先の確認方法

Supabase ダッシュボードの Connect から **Session pooler**（ポート 5432）の情報を取得する。

- **Direct connection（`db.<ref>.supabase.co`）は使えない。** IPv6 のみの場合があり、
  GitHub Actions のランナー（IPv4）から到達できない
- **Transaction pooler（ポート 6543）も使えない。** `pg_dump` はセッションを跨ぐ操作を行うため
- ユーザー名は **`postgres.<project-ref>`**。pooler 経由では単なる `postgres` では認証に失敗する

Connect ダイアログにタブが見当たらない場合は、接続方式のドロップダウンから Session を選ぶ。
Transaction pooler の文字列が表示されているなら、**ポートを 6543 → 5432 に変えるだけ**で
Session pooler の接続先になる（ホスト名とユーザー名は共通）。

#### パスフレーズの生成

```bash
openssl rand -base64 32
```

**このパスフレーズを失うとバックアップは永久に復号できない。**
パスワードマネージャ等、GitHub とは別の場所に必ず保管すること。
データベースパスワードも同様に、失うとリセットしか手段がない。

#### 登録

```bash
gh secret set SUPABASE_DB_HOST
gh secret set SUPABASE_DB_USER
gh secret set SUPABASE_DB_PASSWORD
gh secret set BACKUP_PASSPHRASE
```

対話入力が使えない環境では、シェル履歴に残らないよう次の形で登録する。

```bash
read -rs SECRET && printf '%s' "$SECRET" | gh secret set SUPABASE_DB_PASSWORD && unset SECRET
```

`printf '%s'` を使うのは、末尾に改行が混入するのを防ぐため。

### 2. 手動実行して動作を確認する

```bash
gh workflow run backup.yml
gh run list --workflow backup.yml --limit 1
```

### 3. 復旧できることを一度検証する ★必須

**未検証のバックアップは、無いのと同じ。** 復元手順の初回実行が「データを失った直後」になると、
外部キー制約や `auth` スキーマの欠落といった問題を、最も余裕のない状況で初めて踏むことになる。

検証は自動化してある。使い捨ての PostgreSQL コンテナへ実際に流し込み、件数と参照整合性を確認する。
**本番DBには一切書き込まない。**

```bash
gh workflow run verify-restore.yml          # 直近の成功バックアップを検証
gh workflow run verify-restore.yml -f run_id=<run-id>   # 特定の実行を検証
gh run watch
```

検証内容：

- 復号・展開できること
- `auth.users` を復元できること（プロジェクト全損時の復旧経路）
- `public.sql` がエラーなく流し込めること
- `goals` / `sub_goals` / `tasks` / `emotion_logs` が 0 行でないこと
- 親レコードを参照できない行が無いこと

**ログには件数しか出力しない。** 公開リポジトリの Actions ログに感情ログの中身を残さないため。

手作業で中身まで目視したい場合は `scripts/restore-db.sh` で復号・展開する
（展開した平文ファイルは確認後に必ず削除すること）。

## 日常の運用

### マイグレーション適用前

**必ず手動でバックアップを取る。** 最も現実的な事故がここで起きる。

```bash
gh workflow run backup.yml
```

完了を確認してからマイグレーションを適用する。

**適用後は復元検証を1回回す。**

```bash
gh workflow run verify-restore.yml
```

復元可能性が変わるのはスキーマが変わったときであり、データが1日分増えたときではない。
そのため検証は定期実行にせず、この「スキーマを変えた直後」に実行する運用にしている。

### 定期確認（月1回程度）

```bash
gh run list --workflow backup.yml --limit 10
```

成功が並んでいること、アーカイブのサイズが極端に小さくなっていないことを確認する。
スクリプトは 1KB 未満のアーカイブをエラーとして扱うが、目視確認も併用する。

## 復旧手順

1. 対象の Artifacts をダウンロードする
2. `scripts/restore-db.sh` で復号・展開する
3. **中身を確認する**（想定した日付範囲のデータが入っているか）
4. 接続先が復旧対象のプロジェクトであることを確認したうえで、手動で流し込む

```bash
PGPASSWORD='...' psql \
  --host=aws-0-<region>.pooler.supabase.com \
  --port=5432 \
  --username=postgres.<project-ref> \
  --dbname=postgres \
  --file=restored/public.sql
```

接続文字列（URL）にパスワードを埋めないこと。記号が壊れるうえ、
エラー時にパスワードが出力される。

`public.sql` は `--clean --if-exists` 付きで作られているため、
**既存の public スキーマのテーブルを削除してから作り直す。**
実行先を間違えると本番データを消す。接続文字列を必ず確認すること。

復旧を自動化していないのは意図的である。復旧は上書き操作であり、
自動化すると誤実行時の被害が大きくなるため、人間が中身を見てから実行する設計にしている。

### プロジェクトごと失った場合

`auth.users` のダンプが必要になる。`goals.user_id` は `auth.users(id)` を参照しているため、
ユーザー行を先に復旧しないと外部キー制約で失敗する。

1. 新しい Supabase プロジェクトを作成し、`supabase/migrations/` を適用する
2. `auth_users.sql` を流し込む
3. `public.sql` を流し込む

`auth_users.sql` はベストエフォートで取得しているため、存在しない場合がある
（その場合はアーカイブ内に `auth_users.SKIPPED` が入っている）。
この経路は Supabase 側の内部スキーマ変更に影響を受けやすいので、
プロジェクト全損は「keep-alive とプラン移行で予防する」ことを主とし、
このバックアップは最後の手段と位置づける。

## 制約

- **Artifacts の保持期間は最大90日。** それより長く残したい時点のバックアップは、手動でダウンロードして保管する
- **GitHub 上に暗号化データが置かれる。** パスフレーズの強度と保管がそのまま安全性になる
- **`auth.users` の復旧はベストエフォート。** 上記の通り
- 保存先を GitHub 以外（自己管理ストレージ等）に変えたい場合は、`backup.yml` のアップロード先を差し替える
