# ブランチ戦略

このドキュメントは comeback-log リポジトリにおけるブランチ運用ルールを定めるものです。
運用方針に変更が生じた場合は、このドキュメントを更新すること。

## 1. 前提

- 現時点では開発者1名（+ Claude Code によるペアプログラミング）による個人開発。
- CI は GitHub Actions で導入済み（`.github/workflows/ci.yml`）。`main` への push / PR で
  Lint（`npm run lint`）・型チェック（`npm run typecheck`）・テスト（`npm test`）を実行する。
  CD（EAS Build/Update 等による自動配信）は未導入。
- Supabase 環境は本番用の1系統のみ（dev/staging/prod の分離なし）。
- Expo による配布は EAS/Expo Go を用いた継続的なビルド想定であり、決まったリリース周期（週次リリース等）は存在しない。
- `CLAUDE.md` に定義された **Phase 1 → Phase 2 → Phase 3** の段階的な機能追加が開発の基本単位になる。

これらの前提から、`develop` ブランチや `release/*` ブランチを持つ Git-flow 型の運用は
オーバーヘッドが大きく本プロジェクトには適さない。**トランクベース開発（GitHub Flow に準拠した軽量運用）** を採用する。

## 2. 基本方針

- `main` ブランチは常にデプロイ可能な状態を保つ（動作する状態でしか merge しない）。
- すべての変更は `main` から切った短命の作業ブランチ上で行い、Pull Request 経由で `main` にマージする。
- 作業ブランチは長くても数日以内にマージし、放置しない。長期化しそうな場合はタスクを分割する。
- `develop` や `release/*` などの長期ブランチは作らない。

## 3. ブランチ種別と命名規則

| 種別 | プレフィックス | 用途 | 例 |
|---|---|---|---|
| 機能追加 | `feat/` | 新機能・新画面の実装 | `feat/emotion-log-tag-input` |
| 不具合修正 | `fix/` | バグ修正 | `fix/goal-tree-checkin-crash` |
| リファクタリング | `refactor/` | 挙動を変えない内部改善 | `refactor/insights-rule-engine` |
| ドキュメント | `docs/` | ドキュメントのみの変更 | `docs/branch-strategy` |
| 雑務 | `chore/` | 依存更新・設定変更など | `chore/upgrade-expo-sdk` |
| DBマイグレーション | `migration/` | Supabaseスキーマ変更を含む作業 | `migration/add-public-profile-table` |

- 名前は英語・ケバブケースで、内容が一目でわかる短い説明を付ける。
- どの `CLAUDE.md` フェーズに属する作業かは、ブランチ名ではなく Issue / PR 説明文に明記する
  （フェーズをブランチ名に固定すると、フェーズ跨ぎのリファクタ等がしづらくなるため）。

## 4. 日常のワークフロー

1. `main` を最新化する（`git pull origin main`）。
2. `main` から作業ブランチを切る（例: `git checkout -b feat/xxx`）。
3. 作業ブランチ上でコミットを積む（コミット規約は6章を参照）。
4. 作業が完了したら `origin` に push し、Pull Request を作成する。
5. 個人開発のため必須レビュワーは立てないが、マージ前に `/code-review` を通す
   （設計変更やDBスキーマ変更を伴う場合は `/code-review high` 以上、または `ultrareview` を推奨）。
6. Pull Request を **Squash and merge** で `main` に統合し、作業ブランチは削除する。
7. `main` への直push は、ドキュメントの誤字修正など「レビューする意味がないほど自明な変更」に限り許容する。
   実装・DBマイグレーションを含む変更は必ず PR を経由する。

## 5. マージ方法

- **Squash merge** を基本とする。作業ブランチ内の試行錯誤コミットを1つにまとめ、`main` の履歴を読みやすく保つ。
- Squash 後のコミットメッセージは PR タイトルをそのまま使う（6章の規約に従ったタイトルにする）。
- Fast-forward や merge commit は使わない（GitHub の Squash and merge 設定に統一する）。

## 6. コミットメッセージ規約

既存の commit log（`feat:` `fix:` `chore:` `docs:` `style:` ...）に倣い、
[Conventional Commits](https://www.conventionalcommits.org/) 形式を踏襲する。

```
<type>: <変更内容の要約（命令形・日本語可）>
```

主な `type`:

| type | 用途 |
|---|---|
| `feat` | 機能追加 |
| `fix` | 不具合修正 |
| `refactor` | 挙動を変えないコード改善 |
| `docs` | ドキュメントのみの変更 |
| `chore` | 依存関係・設定など |
| `style` | 見た目・フォーマットのみの変更（ロジック変更なし） |
| `test` | テストの追加・修正 |

## 7. タグ・バージョニング

- 現時点では正式なリリースタグ運用は行わない（`package.json` / `app.json` の version は Phase 完了などの節目で手動更新）。
- 各 `CLAUDE.md` の Phase が完了し動作確認が取れた時点で、`v0.1.0-phase1` のような注釈タグを打つことを推奨する
  （後から挙動を追いにくくなるのを防ぐための目印であり、厳密な SemVer 運用は求めない）。

## 8. Supabase マイグレーションに関する注意

- `supabase/migrations/` を変更する PR は、必ず `migration/` プレフィックスの専用ブランチで行い、
  他の機能変更と混在させない。
- マイグレーションはロールバック困難な操作（カラム削除・型変更等）を含みうるため、
  マージ前に本番相当データでの動作確認、または Supabase ダッシュボード上でのSQLレビューを行う。
- `EmotionLog` 関連テーブルのアクセス権限（RLS）を変更するマイグレーションは、
  `CLAUDE.md` の「感情ログのプライバシーを最優先する」方針に反していないか PR 説明文で明示的に確認する。

## 9. 将来的な拡張（現時点では未実施）

以下は当面不要だが、状況が変わった場合に検討する拡張。

- **ブランチ保護の有効化**：CI（lint / typecheck）は導入済み。GitHub のブランチ保護ルール
  （Required status checks）を有効化し、CI が通らない PR を `main` にマージできないようにする。
- **開発者が増えた場合**：レビュー必須化（Required reviewers）を追加する。ただし `develop` ブランチの導入は
  それだけでは正当化せず、リリース周期が固定化された場合に改めて検討する。
- **Phase 3（公開プロフィール機能）以降、複数環境が必要になった場合**：
  Supabase の dev/prod プロジェクト分離と合わせて、環境ごとのデプロイブランチ運用を再検討する。
