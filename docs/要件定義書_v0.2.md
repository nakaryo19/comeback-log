> このドキュメントは相談しながら更新してきたものです。v0.1からの主な変更点は、AIコーチング機能を撤廃し、完全無料運営を前提とした可視化中心の設計に切り替えたことです。

## 1. プロダクト概要

| 項目 | 内容 |
|---|---|
| プロダクト名（仮） | 挽回ログ |
| コンセプト | 目標達成までのタスク管理と感情ログを紐づけて記録し、**タスクの実績と感情の波の相関を可視化することで、自分自身の"攻略法"に気づける**、再挑戦者のための記録アプリ |
| フェーズ | 最初から一般公開前提で設計 |
| プラットフォーム | Web + モバイル（クロスプラットフォーム） |
| マネタイズ | なし（個人開発・実験プロジェクトとして無料公開、AI APIを使わないため運用コストはほぼゼロ） |

---

## 2. ターゲットユーザー像

- 浪人、再受験、キャリア再構築、ダイエットや資格取得の再挑戦など、**「一度うまくいかなかったことに、もう一度向き合っている人」**
- 目標達成の過程で、モチベーションのアップダウンが激しく、**「なぜ続かなかったのか／なぜ頑張れた日があったのか」を自分で言語化するのが苦手**な人
- Notionやタスク管理アプリを試したことはあるが、**「タスクの消化率」だけでは自分の状態を説明しきれず挫折した経験**がある人

### ペルソナ例（叩き台）
- 26歳、公務員試験に再挑戦中。日中は勉強、夜は不安で手につかない日がある。タスクは完了しているのに「なんとなく調子が悪い週」がある理由を知りたい。

---

## 3. コンセプト・差別化ポイント

既存の目標管理／習慣化アプリ（Notion、Todoist、継続する技術、Finc等）との違い：

| 既存アプリ | このアプリ |
|---|---|
| タスクの完了/未完了を記録するだけ | タスクの実績と感情ログを**同じ時間軸に紐づけて可視化** |
| 「頑張れたか」は主観的な振り返りに依存 | **データとして相関パターンを可視化**し、気づきはユーザー自身に委ねる |
| コーチングは定型的なリマインド中心 | グラフ・ヒートマップなど**視覚的な自己分析ツール**として機能 |

**コア体験の一言表現（案）**：
「頑張った記録」と「しんどかった記録」を両方残すことで、"根性論ではない自分の攻略法"が見えてくるアプリ

## 4. コア機能（MVP スコープ）

### 4-1. タスク管理

- 大目標 → 中目標 → 日次タスクへの分解（ゴールツリー構造、データ構造上は常に3階層を維持）
- **大目標は複数持てる。** 並行して追いかけている目標（例：「AWS認定資格を取得する」と「個人開発アプリをリリースする」）を分けて管理できる
- 日次タスクのチェックイン（完了／未完了／部分達成）
- 進捗の可視化（達成率、連続日数など）

#### ゴールツリーの入力フロー

初回登録のハードルを下げつつ、データ構造としては中目標を必須とするため、**仮の中目標を自動生成する方式**を採用する。

**初回登録（オンボーディング）**
1. 大目標を入力（例：「公務員試験に合格する」）
2. 今日やることを1つ以上入力（自由記述→自動でタスク化）→ 裏側で仮の中目標（例：「ステップ1」）を自動生成し、そのタスクを紐付ける
3. 登録完了、ホーム画面へ

**目標管理画面（後から整理する場）**
- 仮の中目標を選び、名前を編集（例：「一次試験対策」）
- 中目標を追加作成（例：「二次試験対策」「体力試験対策」）
- 既存タスクを別の中目標に付け替え
- 2つ目以降の大目標を追加作成（オンボーディングと同様に仮の中目標を自動生成し、3階層を維持する）
- 大目標の名前を編集

**日次タスクの追加**
- 日付を指定した個別タスクとして追加（例：「7/15 模試を受ける」）
- 追加時にどの中目標に紐付けるか選択（未指定の場合は直近の仮中目標に自動割り当て）

### 4-2. 感情ログ（タスク完了と1:1で紐付け）

タスクを完了操作した直後、その場に軽量な入力UIが自然に現れる（別画面遷移なし・プッシュ通知は使わない）。

| 入力項目 | 必須/任意 | 内容 |
|---|---|---|
| スコア | 必須・ワンタップ | 1〜5段階（絵文字や色のグラデーションなど直感的なUI） |
| タグ | 任意・ワンタップ | 不安／達成感／焦り／集中／疲労 などから1つ選択 |
| 自由記述 | 任意・展開式 | 「もう少し書く」ボタンで展開。書かなければスキップ |

「必須は2タップ以内」を徹底し、継続率を担保する。

### 4-3. 可視化ダッシュボード（AIコーチングに代わるコア機能）

自然言語によるAI生成ではなく、**グラフ・集計・ルールベースのハイライト表示**によって「気づきはユーザー自身に委ねる」体験を実現する。

「毎日サクッと確認したい」と「分析ツールとして深く振り返りたい」という相反するニーズを両立するため、**2層構造**で設計する。

#### 層1：ホーム画面（毎日サッと見る）
- 直近7日間に絞った、相関散布図（横軸：1日のタスク完了数、縦軸：感情スコア）をメインに表示
- 週次サマリーカード2枚（今週の達成率／平均感情スコア）を添える程度に留め、1画面・数秒で完結する情報量に絞る
- 「詳しく見る」導線から層2へ遷移

#### 層2：詳細分析画面（じっくり振り返りたい時に見る）
情報密度を上げ、分析ツールとしての実用性を優先した構成。

| 機能 | 内容 |
|---|---|
| 感情スコア・カレンダーヒートマップ | 1ヶ月分を俯瞰し、感情スコアの高低を色の濃淡（青の濃淡）で表示 |
| 週次サマリーリスト | 週ごとの達成率・平均スコアを一覧表示 |
| ハイライト表示（ルールベース） | あらかじめ用意した条件×固定バッジで「好調週」等を機械的にマーク（例：達成率上位20%の週に★バッジ）。AI生成ではなく単純な条件分岐でコスト0 |
| 感情タグの推移グラフ | タグ（達成感・不安・集中など）の週別出現数を積み上げ棒グラフで表示し、変化を視覚化 |

**この設計により、AI APIを一切呼ばない構成となり、運用コストは完全にゼロになる。感情ログが外部AI APIに送信されることもないため、プライバシー面でも「自分だけの記録」という安心感を担保できる。**

#### ハイライト表示のルール設計

好調週だけでなく不調週も検出するが、評価的にならないよう表現面を含めて慎重に設計する。

**最低データ量**：相対評価には母数が必要なため、**最低4週間分**のデータが蓄積されるまでハイライト自体を表示しない（それまでは集計数値のみ表示）。

**判定指標**：週次の「達成率」と「平均感情スコア」を組み合わせた複合スコアを用いる（加重平均、重みは後で調整可能な設計にする）。

**好調週・不調週の判定ルール**

| 区分 | 条件 | 表現 |
|---|---|---|
| 好調週 | 複合スコアが自分の過去データの**上位20%**以内 | 「★ 好調週」バッジ（詳細分析画面の週次サマリーリストに表示） |
| 不調週 | 複合スコアが自分の過去データの**下位20%**以内 | バッジ化・評価的な言葉（「不調」「低調」等）は使わず、労いのトーンの控えめなテキストカードで1つだけ表示（例：「ちょっとペースが落ちていたかも」「無理してたかもしれません」） |
| 通常週 | それ以外 | 表示なし（サマリー数値のみ） |

**相関パターンの検出（タスク量×感情）**：単一週の集計に加え、テンプレート文＋条件分岐で以下のようなパターンも検出する（AI生成不要）。

| パターン名 | 検出条件（案） | メッセージ例 |
|---|---|---|
| 詰め込みパターン | タスク完了数が平均+1件以上だった日の翌日、感情スコアが週平均を下回る、が週内2回以上 | 「タスクを詰め込んだ翌日は、少しペースが落ちる傾向があるようです」 |
| 好循環パターン | 感情スコアが高い日の翌日、タスク完了数も平均以上、が週内2回以上 | 「調子が良い日は、次の日の勢いにもつながっているようです」 |

**設計思想**：不調週の検出は「ダメ出し」ではなく「労い・気づきの提供」であることを徹底する。評価的な言葉やアラート色（赤・強い黄）は避け、責めない・観察を促す言い回しと落ち着いた配色に留める。

### 4-4. ソーシャル要素（進捗の任意公開）

感情ログは完全非公開。進捗（達成率・継続日数など）のみ、任意で公開可能にする「発信重視」の設計。

| 機能 | 内容 |
|---|---|
| 公開プロフィール（任意） | 目標名、挑戦テーマ、達成率や継続日数などのサマリーを公開できる |
| 公開・非公開の切り替え | デフォルトは非公開。ユーザーが明示的にONにした場合のみ公開（オプトイン方式） |
| 公開範囲の限定 | 感情ログ・自由記述は、公開設定をONにしても**絶対に公開されない**（データベース／アクセス権限レベルで構造的に分離） |
| 閲覧のみ | 他人の公開プロフィールを閲覧できる導線（一覧・検索等）。コメントや応援ボタン等のインタラクションはMVPでは含めない |

**将来の拡張として切り離すもの**：応援コメント／リアクション機能、仲間・コミュニティ機能

## 5. 技術スタック

| レイヤー | 選定 | 理由 |
|---|---|---|
| フロントエンド | **React Native (Expo) + react-native-web** | Reactの開発経験を活かしつつ、iOS/Android/Webを単一コードベースでカバー。Expoで環境構築・配信の手間も削減 |
| バックエンド/DB | **Supabase**（PostgreSQL + Auth + Storage） | 無料枠が手厚く、個人開発・無料公開との相性が良い。認証・DB・ファイル保存が最初から揃っている |
| 相関分析・集計処理 | **クライアント側 or Supabase Edge Functionsでの軽量ロジック** | AI API不使用のため、統計処理（相関係数計算、条件分岐によるハイライト判定など）のみで完結。外部AI APIへの依存なし |

### v0.1からの変更点
- AIコーチング処理（Anthropic API / Gemini API呼び出し）を撤廃
- `CoachingReport` テーブル・API連携部分が不要に
- **APIコスト管理の設計自体が不要**（外部AI APIを呼ばないため）

---

## 6. 非機能要件

- **運用コスト**：AI API不使用により、Expo（無料枠）＋Supabase（無料枠）のみで完全無料運営が可能
- **クロスプラットフォーム開発コスト**：React Native (Expo) + react-native-webにより、Web/モバイルをほぼ単一コードベースで開発
- **プライバシー**：感情ログ・自由記述は外部送信されず、アプリ内（Supabase）にのみ保存。公開プロフィールとのデータ分離をDB設計レベルで徹底

## 7. データモデル

```
User
 └─ Goal（大目標、複数可）
     └─ SubGoal（中目標、必須。初回登録時や大目標の追加時は「仮の中目標」を自動生成）
         └─ Task（日次タスク）
              - status（完了/未完了/部分達成）
              - date

EmotionLog
 - user_id
 - task_id          ← タスクと1:1で紐付け
 - datetime
 - score（1-5、必須）
 - tag（1つ、任意）
 - free_text（任意）

PublicProfile（任意公開）
 - user_id
 - goal_summary（目標名・挑戦テーマ）
 - achievement_rate
 - streak_days
 - is_public（デフォルトfalse）

※ 感情ログ・自由記述は PublicProfile から参照不可（アクセス権限で構造的に分離）
```

**v0.1からの変更点**：`CoachingReport` テーブルを削除（AI生成コンテンツを保持する必要がなくなったため）

## 9. MVPスコープ（フェーズ分け）

開発に割ける時間が週数時間程度と限られていること、また「まず自分自身が既存の『挽回ログ』から乗り換えて使い始める」ことを最初の成功基準とすることを踏まえ、機能を3フェーズに分けてリリースする。

### Phase 1：MVP（最初にリリースする範囲）
**目的**：自分自身が日常的に使い始められる状態にする

| 機能 | 範囲 |
|---|---|
| タスク管理 | ゴールツリー（大目標→仮の中目標→日次タスク）、チェックイン |
| 感情ログ | タスク完了と1:1紐付け、スコア＋タグ＋自由記述（展開式） |
| 可視化 | 最小限のみ：ホーム画面に今週の達成率・平均スコアの数値表示程度（グラフは含めない） |

技術スタック（React Native/Expo + Supabase）を用いてこの3点をシンプルに実装し、実際に1〜2週間使ってみて記録が続くかを検証する。

### Phase 2：可視化ダッシュボード強化
- 2層構造ダッシュボード（ホーム＝簡易な相関散布図、詳細分析＝ヒートマップ・タグ推移）
- ハイライト表示のルール実装（好調週／不調週の労いメッセージ、タスク量×感情の相関パターン検出）

Phase 1で記録の継続を確認し、数週間分のデータが蓄積されてから着手する（可視化・ハイライトはデータが少ないと価値が出ないため）。

### Phase 3：公開・ソーシャル要素
- 公開プロフィール機能（達成率・継続日数などの任意公開、感情ログは非公開のまま）
- 他人の公開プロフィールの閲覧

自分以外のユーザーに使ってもらう段階になってから着手する。

## 10. 決定済みの論点（まとめ）

- [x] 技術スタック：React Native (Expo) + Supabase
- [x] 感情ログの入力UX：タスク完了と1:1紐付け、2段階入力（軽量必須＋任意の自由記述展開）
- [x] AIコーチング：**撤廃**。可視化ダッシュボード（ルールベースのハイライト含む）に置き換え
- [x] ソーシャル要素：進捗サマリーのみ任意公開、感情ログは非公開を構造的に担保
- [x] 運用コスト：AI API不使用により実質ゼロ
- [x] 可視化ダッシュボードのUI/UXデザイン：2層構造（ホーム＝簡易・詳細分析＝高密度）で確定
- [x] ハイライト表示のルール設計：相対評価（上位/下位20%）、不調週は労いトーンで控えめに表現、タスク量×感情の相関パターン検出も含む
- [x] ゴールツリーの入力フロー：初回は大目標＋今日のタスクのみ、仮の中目標を自動生成してデータ構造上は3階層を維持
- [x] 大目標の複数保持：並行する目標を分けて管理できるようにする（目標管理画面から追加。追加時も仮の中目標を自動生成）
- [x] MVPスコープ：Phase 1（タスク管理＋感情ログ＋最小可視化）→ Phase 2（2層ダッシュボード＋ハイライト）→ Phase 3（公開・ソーシャル）の3段階に分割

## 11. 今後の論点

現時点で、主要な論点はすべて確定済み。今後は Phase 1 の実装を進める中で、細部の仕様（バリデーション、エラーハンドリング、具体的な画面デザインの詰めなど）を随時相談していく想定。
