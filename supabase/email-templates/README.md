# 認証メールのテンプレート

Supabase Auth が送るメールの本文。**このディレクトリが正本**で、
Supabase ダッシュボードの **Authentication → Emails** に貼り付けて反映する。

ダッシュボードだけを直すと差分が追えなくなるため、変更するときは
必ずファイルを先に直し、そのうえで貼り替えること。

| ファイル | ダッシュボードの貼り付け先 | 件名（Subject heading） | 状態 |
|---|---|---|---|
| `reset-password.html` | Reset Password | `【挽回ログ】パスワード再設定のご案内` | 使用中 |
| `confirm-signup.html` | Confirm signup | `【挽回ログ】メールアドレスのご確認` | 使用中 |

**件名は本文とは別のフィールド**で、本文だけ貼り替えても既定の英語が残る。
テンプレートごとに保存ボタンが分かれている点にも注意する。

差し替えは**保存後に送信されるメールから**効く。確認するときは、
保存したうえで新しく1通送ること。Gmail は同じ件名のメールを
1つのスレッドにまとめるため、古いメールを開いていないか受信時刻で確かめる。

## ダッシュボード側で必要な設定

確認メールは、テンプレートを貼るだけでは送られない。次の2つが揃って初めて機能する。

1. **Authentication → Sign In / Providers → Email → Confirm email を ON**
   （既定は OFF＝自動確認。OFF のままだと未検証のアドレスで本登録できてしまう）
2. **Authentication → URL Configuration → Redirect URLs に確認リンクの戻り先を登録**
   - `comebacklog://auth/confirm`（開発ビルド・本番アプリ）
   - `exp://*/--/auth/confirm`（Expo Go で確認する場合）
   - Web の戻り先はオリジンそのもの（`lib/supabase/auth-links.ts` を参照）

登録し忘れると、リンクを踏んでもアプリに戻らず、利用者からは
「メールは届くのに登録が終わらない」という状態に見える。

## なぜ差し替えるか

Supabase の既定テンプレートは英語で、日本語話者向けのアプリで送ると
「心当たりのない英文メール」になる。パスワード再設定メールは
フィッシングと形が似ているため、読み手が真偽を判断できる文面である必要がある。

## 書くときの制約

**ファイルの中に HTML コメントを置かない。** 解説はこの README に書く。
テンプレートはダッシュボードへ丸ごと貼り付けるものなので、
ファイルの中身がそのまま貼れる状態でないと、貼るたびに手で削ることになる。


- **外部の画像・フォントを読み込まない。** メールクライアントは既定で外部リソースを
  止めるうえ、読み込ませることは開封を送信側に伝えることでもある
- **CSS は `style` 属性に直接書く。** 多くのクライアントが `<style>` ブロックを落とす
- **レイアウトは `<table>` で組む。** flexbox / grid は Outlook 系で崩れる
- 差し込み変数は Supabase の記法（`{{ .ConfirmationURL }}` など）

## 送信経路

送信は Brevo の SMTP リレー経由（`smtp-relay.brevo.com:587`）。
Supabase 組み込みの送信はプロジェクトのチームメンバー宛にしか配信されず、
一般の利用者がパスワードを復旧できないため使えない。

**独自ドメインを持たない構成のため SPF / DKIM を張れていない。**
迷惑メールに振り分けられる可能性が残っており、アプリ側の送信完了文言でも
迷惑メールフォルダの確認を案内している（`components/auth/AuthScreen.tsx`）。
